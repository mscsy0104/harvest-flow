# 💡 옵시디언의 '독점성' 우려를 깨부수는 3가지 오픈소스 전략

## 1. 데이터 포맷의 본질: 옵시디언은 결국 '순수 마크다운(Markdown)'이다

옵시디언의 가장 큰 장점이자 본질은 데이터를 자체 서버에 숨겨두지 않고, 사용자의 로컬 드라이브에 **순수 마크다운(`.md`) 파일 구조**로 저장한다는 점입니다.

- **어필 포인트:** "특정 툴에 종속된 프로젝트가 아니라, '로컬 마크다운 기반의 개인 지식 베이스(PKM)를 위한 데이터 파이프라인'을 만들었다"라고 정의하는 것입니다.
    
- 이렇게 하면 옵시디언뿐만 아니라 **Logseq, Foam, VS Code 등 마크다운 기반의 다른 오픈소스 노트 앱 사용자들도 그대로 가져다 쓸 수 있는 확장성**을 갖추게 됩니다.
    

## 2. 프로젝트의 정체성을 '플러그인'이 아닌 '인프라 프레임워크'로 설정하기

만약 옵시디언 앱 안에서만 돌아가는 전용 플러그인(JavaScript)을 만들면 특정 회사 서비스에 종속적이라는 비판을 받을 수 있습니다.

- **해당하는 해결책:** 옵시디언은 그저 '데이터가 쌓이는 소스(Source) 저장소'일 뿐이고, 본인의 프로젝트는 독립적으로 실행되는 파이프라인 엔진(Docker 컨테이너 또는 Python 패키지)으로 설계하는 것입니다.
    
- "로컬의 특정 폴더를 감시(Watch)하다가 파일이 변경되면 벡터화하고 블로그로 쏘는 엔지니어링 인프라"가 핵심이 되므로, 특정 서비스 종속성 논란에서 완벽히 자유로워집니다.
    

## 3. '오픈소스 대안(Alternative)' 호환성 한 줄 추가하기 (치트키)

README 문서나 아키텍처 구성도에 다음과 같은 확장성을 명시하면 심사위원들이 감탄합니다.

> _"본 프로젝트는 로컬 디렉토리의 표준 마크다운 구조를 파싱하므로, 옵시디언(Obsidian)뿐만 아니라 완전한 오픈소스 노트 앱인 **Logseq**이나 **AppFlowy**의 로컬 저장소와도 100% 호환됩니다."_

# 📋 면접관과 심사위원을 설득할 방어 논리 요약

대회 발표나 이직 면접 때 이 질문이 나온다면 이렇게 답변하시면 백점짜리 답변이 됩니다.

> **"옵시디언은 클라이언트 툴일 뿐, 본 프로젝트의 핵심은 '로컬 표준 마크다운 데이터의 변경 사항을 감지하여 가공·적재하는 증분 데이터 파이프라인(CDC)'과 '로컬 LLM 아키텍처'의 구현에 있습니다. 따라서 소스 저장소가 옵시디언이든, 오픈소스인 Logseq이든, 혹은 리눅스 서버의 일반 마크다운 폴더이든 상관없이 작동하는 범용적인 오픈소스 프레임워크입니다."**

**결론적으로, 전혀 걱정하실 필요 없습니다.** 오히려 현업 엔지니어들은 현실 세계의 유명한 도구(옵시디언)와 오픈소스 인프라를 매끄럽게 연동하여 실용적인 가치를 만들어내는 프로젝트를 훨씬 더 높게 평가합니다.
