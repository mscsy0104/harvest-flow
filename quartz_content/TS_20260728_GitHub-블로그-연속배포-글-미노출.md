## 3. 원인

- 23:41에 **두 글이 11초 간격으로 연속 배포**됨
- `deploy.yml`의 `concurrency.cancel-in-progress: false` 때문에 두 배포가 **직렬 처리**됨
  1. 먼저 TS 커밋 배포 실행 → Wiki 글이 **없는** 스냅샷을 먼저 게시
  2. Wiki 커밋 배포는 앞 배포가 끝날 때까지 **큐에서 대기**했다가 그 후 실행
- 따라서 push 완료(23:41:40) 이후에도
  `① TS 빌드 완료 → ② Wiki 빌드 시작·완료 → ③ GitHub Pages CDN 반영`
  까지 **수 분(약 4~8분)** 소요됨
- 그 사이(특히 TS 배포만 끝난 시점)에 확인하면 Wiki 글이 안 보이게 됨
- 브라우저/CDN 캐시가 겹치면 체감 지연이 더 길어짐
- **결론: 데이터 유실·버그가 아니라 "연속 배포 시 직렬 처리로 인한 반영 지연"**

## 4. 해결 (명령어 포함)

### 4-1. 즉시 조치 — 이미 배포 완료 상태 확인 후 새로고침

- 조사 결과 이미 라이브에 정상 노출 중이므로, 캐시만 강제 갱신하면 됨
- 브라우저에서 강력 새로고침: `Cmd + Shift + R` (macOS)

```bash
# 캐시 우회로 최신 반영 확인
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://mscsy0104.github.io/harvest-flow/wiki_airflow-dag-이름-작성-팁?nocache=$(date +%s)"
```

### 4-2. 근본 해결 — 연속 배포 시 최신 빌드만 반영되도록 동시성 설정 변경

- 각 배포는 **매번 전체 콘텐츠를 새로 빌드**하므로, 진행 중인 오래된 빌드는 취소하고
  최신 커밋(모든 글 포함) 기준 빌드 1회만 남기면 최종 상태 도달이 빨라짐
- `.github/workflows/deploy.yml` 수정:

```yaml
concurrency:
  group: pages
  cancel-in-progress: true   # false → true
```

- 효과:
  - Wiki push가 들어오면 진행 중이던 TS 빌드를 취소
  - 두 글이 모두 포함된 최신 빌드 **1회만** 실행 → 반영 지연 최소화
  - 최종 배포 커밋이 항상 전체 스냅샷이라 도중 취소되어도 안전

### 4-3. 변경 사항 커밋·배포

```bash
git add .github/workflows/deploy.yml
git commit -m "fix(ci): 연속 배포 시 최신 빌드만 반영되도록 cancel-in-progress 활성화"
git push origin main
```
